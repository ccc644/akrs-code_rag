# 简历更新与面试项目介绍

更新日期：2026-10-19。本文按当前代码实际能力撰写，覆盖 Python-only 改造后的状态；未测量的准确率、延迟和幻觉下降幅度不写入简历。

## 1. 简历项目条目（推荐版）

**ARKS 智能助手｜面向源码理解与调试知识复用的 RAG Agent**（个人 / 实习项目）

技术栈：Python、LangGraph、Deep Agents、Tool Calling、FastEmbed、NumPy、SQLite；FastAPI、React 用于应用交付。

- **多源混合检索：** 为项目资料、交接资料和调试记录构建检索索引，融合本地多语言 Embedding（FastEmbed / MiniLM）、词面倒排、领域同义词扩展（原词 1 分、扩展词 0.25 分）和标题加权；按 `lexical + 3×title_overlap + 3×semantic` 融合排序，无词面命中要求语义相似度 ≥ 0.6；向量按模型与文本指纹缓存到 SQLite，Embedding 不可用时自动降级为词面检索。
- **Agent 工具编排：** 基于 Deep Agents / LangGraph 构建单 Agent 工具调用工作流，整合源码按行读取、批量读取、全文搜索、Python AST 符号与调用关系分析、知识检索和长期记忆工具；用检索预算控制工具调用次数并为关键证据复核预留额度，用 SQLite checkpointer 支持断线恢复与"继续运行"。
- **回答溯源与复核：** 为每次源码读取绑定 SHA-256 文件版本与行号范围；发送前重新核对代码选区，文件变化即标记 stale；最终回答的 `source:path#Lx-Ly` 引用必须覆盖实际读取范围，`SourceEvidenceGuard` 在最多两次补读修复后仍无法核实的引用会被降级并明确提示；另用独立步骤复核结论中的条件与调用顺序。
- **上下文与长期记忆：** 在 token 预算内注入检索片段，对重复工具结果去重压缩；超限时生成摘要并保留原文回查入口；长期记忆按项目事实和用户偏好分别保存，携带来源、更新时间、stale 和冲突状态，并按账号隔离个人偏好。
- **Python 静态分析：** 用标准库 `ast` 实现符号、导入、继承和保守的调用/调用者分析，路径、编码、符号链接和文件大小统一受工作区边界保护，分析过程不导入、不执行被分析代码；以 SWE-agent（NeurIPS 2024）为默认真实项目验证，并为关键流程维护 9 段带版本指纹的源码说明。
- **工程与验证：** 后端约 1.5 万行 Python、60 个测试文件；本次改造后后端 310 项测试通过、前端 190 项测试通过，Ruff 与生产构建通过；知识资料检查会校验源码指纹，防止说明与代码脱节。

版面紧张时的取舍：保留前三条，把"上下文与记忆"压缩成一条，Python 静态分析并入工具编排一条。

## 2. 一分钟项目介绍（口语版）

> 我做的是一个面向源码理解的 AI 助手，解决的是"接手一个陌生项目时，怎么快速找到实现依据"的问题。用户选中代码提问，系统不是直接让模型编，而是把源码、项目资料、历史调试记录和长期记忆检索出来，再交给一个基于 Deep Agents 和 LangGraph 的 Agent，由它决定要不要继续读文件、搜索或者分析 Python 调用关系。为了保证回答可核对，每次读文件都会记录 SHA-256 版本和行号，回答里的源码引用必须真的覆盖读过的范围，否则系统会要求模型补读，实在对不上就把引用降级并提示。资料侧是本地 Embedding 加关键词、同义词和标题加权的混合检索，没有用向量数据库，因为数据量不大、要求可解释；Embedding 不可用时会自动退回词面检索。长对话用 token 预算、摘要压缩和 checkpoint 管理，记忆跨会话保存并标记过期和冲突。实现上大量用了 AI 辅助，我负责需求、方案、检索策略、边界规则和验收。

## 3. 三分钟深入介绍（面试展开版）

按"问题—方案—取舍—验证"四段讲：

**问题。** 大项目源码分散，交接资料和调试记录也不在一个地方；通用聊天模型容易把没读过的代码说得像读过。核心诉求是三个：找得到、说得清、能核对。

**方案。** 分两层。资料层做混合检索：本地 FastEmbed 多语言模型出向量，配合倒排和同义词，调试记录还额外匹配设备、版本、模块和工况。源码层不清洗、不全量塞进上下文，而是做成只读工具，让 Agent 按需读。Agent 是单 Agent 工具调用，不是多 Agent。最后加一道证据门禁：读过的范围才允许被引用。

**取舍。** 第一，为什么不用多 Agent：当前任务边界清楚，单 Agent 加工具预算更可控，多 Agent 的收益没有验证。第二，为什么不用向量数据库：数据量在数千条级别，NumPy 精确余弦就够，SQLite 存向量还能统一做版本缓存和备份。第三，为什么 Python 分析用标准库 AST 而不是 Pyright：目标不是做类型检查器，而是给模型可核对的候选关系；AST 零依赖、离线、行为确定，动态导入和运行时分派明确标未知。第四，为什么源码区只读：避免助手改坏业务代码，也避免"改了但没验证"的虚假完成感。

**验证。** 自动化测试覆盖工具参数错误、路径越界、版本失效、引用覆盖、预算耗尽、断线恢复等边界；知识资料每次构建都校验源码 SHA-256 和片段原文，代码一变就要求重新复核。真实模型回答质量目前还没有系统化离线评估集，这是下一步最该补的。

## 4. 高频追问与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 这是不是 Agentic RAG？ | 是工具驱动的 RAG：系统预置检索，同时允许模型继续调用检索和读源码工具。执行结构是单 Agent。 |
| 混合检索的公式？ | `score = lexical + 3×title_overlap + 3×semantic`；原词命中 1 分、同义词 0.25 分；无词面命中要求语义 ≥ 0.6。 |
| 为什么不用 BM25 / RRF / Reranker？ | 当前是词项加权加余弦融合，没有实现 BM25、RRF 或交叉编码器重排；这些参数是启发式配置，还没做系统性调优实验。 |
| 引用校验能保证答案正确吗？ | 不能。它保证引用指向真实读过的版本和行号；语义正确性由独立的复核步骤和人工抽查兜底，两者分开统计。 |
| 上下文怎么管理？ | token 预算内注入片段；重复工具结果去重；超限时摘要压缩并保留原文回查；跨会话状态用 LangGraph checkpoint，长期事实用记忆文件。 |
| Python 分析能还原调用图吗？ | 不能。它给的是保守候选：同文件按名称匹配、工作区内同名调用者扫描；动态导入、getattr、装饰器和运行时分派都标未知。 |
| 你做了什么、AI 做了什么？ | 需求定义、检索策略、证据规则、边界设计、集成和验收由我负责；具体代码大量使用 AI 辅助，我能解释关键调用链和取舍。 |
| 有什么证据说明有效？ | 310 项后端测试、190 项前端测试、知识资料指纹校验；真实问答质量评估还在计划中，不宣称准确率数字。 |

## 5. 面试演示脚本（5 分钟）

1. 打开项目 `SWE-agent 源码分析`，展示左侧项目与文件树：源码只读，文件树来自 `trunk/swe-agent`。
2. 打开 `sweagent/agent/agents.py`，选中 `DefaultAgent.run`，点"将选区加入对话"。
3. 提问："这个循环什么时候结束？请给出源码引用。"观察事件里的 `read_source` / `python_relations` 调用。
4. 指出回答里的 `source:路径#L行号`，点击跳回源码；展开工具调用，说明读了多少行、版本是多少。
5. 打开"功能说明 → SWE-agent 架构与运行流程"，展示 9 段带 SHA-256 的源码依据，说明代码一改就会提示复核。
6. 提一句边界：这是保守静态分析，不执行被分析代码；真实模型质量评估是下一步。
