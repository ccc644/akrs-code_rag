## 2. 可直接放进简历的版本

**ARKS 智能助手｜源码分析与调试知识 RAG Agent**

**技术栈：** Python、LangGraph、Deep Agents、Tool Calling、FastEmbed、NumPy、SQLite；FastAPI、React 用于应用交付。

- **多源 RAG：** 独立负责源码与调试知识问答系统，针对项目资料、交接资料和调试记录构建混合检索，融合本地多语言 Embedding、关键词倒排、领域同义词扩展与标题加权；按设备、软件版本、报警码及工况检查历史经验的适用性。
- **Agent 工具编排：** 基于 Deep Agents / LangGraph 构建单 Agent 工具调用工作流，整合源码搜索、按行读取、静态关系分析及资料检索，支持模型根据已有结果继续检索和补读，并通过调用预算预留关键证据复核。
- **回答溯源与复核：** 为源码证据绑定 SHA-256 版本及行号范围，校验回答引用的版本一致性和已读覆盖范围；结合有限次数的补读、回答修正和模型语义复核，暴露证据缺失与未确认结论。
- **上下文与记忆：** 在 token 预算内注入检索片段及相关记忆，结合重复工具结果去重、历史摘要、原文回查和 SQLite checkpoint 管理多轮会话；按模型版本与文本内容缓存向量，支持语义检索失败时降级为词面检索。

这四条按 RAG、Agent、可信回答、上下文管理排序。版面紧张时保留前三条，将长期记忆与 checkpoint 合并到 Agent 一条。不必为前端页面、账号管理、常规接口或 Python AST 扩展单独占一条。

## 3. RAG 实现：面试需要讲清楚的内容

### 数据与分块

项目资料、交接资料和调试记录共享混合检索索引；本地源码通过搜索和带行号的读取工具提供直接证据。长期记忆使用语义分数和词面分数排序；内置源码说明也有专门的查询逻辑。不同来源的检索策略并不完全一致。

语义检索在句末标点与换行处分段；超过 100 字符的段落采用长度 100、步长 50 的重叠窗口。这里是字符窗口，不能称作“每块精确 100 token”。查询最多取前四个片段，以片段相似度最大值形成记录级语义分数。

### Embedding 与检索

通过 FastEmbed 本地运行多语言模型 `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，将向量归一化后使用 NumPy 矩阵乘法计算余弦相似度。模型须在本机准备好；问答过程不会自动下载模型。

混合索引使用词项倒排表及领域同义词扩展，原查询词命中计 1 分，扩展词计 0.25 分。最终排序公式为：

```text
score = lexical_score + 3 * title_overlap + 3 * max(0, semantic_similarity)
```

没有词面命中的记录要求语义相似度至少达到 0.6。显式报警码参与筛选；调试记录另外检查设备、软件版本、模块和加热工况，结果标记为条件匹配、条件不符或需要补充条件。

这些权重和阈值是当前启发式配置，尚不能描述为通过系统性实验调优所得。

### 缓存与更新

文档向量保存于 SQLite，缓存键包含模型信息和文本内容指纹；记录目录按版本变动更新正文。当前向量相似度计算使用本地 NumPy 精确扫描，没有采用独立向量数据库或 ANN 索引。

源码引用绑定当前文件的 SHA-256 与行号；资料和调试记录引用绑定记录版本。它们解决的是不同来源的可追溯性。

### 降级与适用性

Embedding 不可用时返回明确的降级信息，词面检索仍可工作。历史记录缺少设备或工况时，返回待核对字段；条件不符的记录可以作为历史对照，但不当作当前适用方案。

## 4. Agent 的技术亮点

- **按需检索：** 系统可以预先带入相关资料，模型也可以继续调用检索与源码工具补齐上下文。这可以表述为工具驱动的 RAG / Agentic RAG；当前执行结构是单 Agent。
- **有界执行：** 检索预算控制调用次数，预留关键源码复核额度；预算用尽时记录尚未核查的范围。
- **证据复核：** 引用校验检查版本与读取覆盖；另用模型核对回答中的条件、分支和调用顺序，失败或不确定时保留提示。模型复核属于独立步骤，当前不构成多个 Agent 的协作系统。
- **状态与记忆：** LangGraph checkpoint 保存运行状态；会话摘要缩减输入，历史回查保留原文入口；长期记忆保存用户偏好和项目事实，并携带来源、状态和冲突提示。
- **工具边界：** 源码工作区只读，不执行未知业务源码；C# Roslyn 与 Python AST 输出供模型定位证据的静态分析结果。

## 6. 高频追问与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 为什么采用混合检索？ | 报警码、模块名和版本号需要精确匹配；用户对同一故障的不同表达需要语义与同义词检索。 |
| 这是 BM25 / RRF 吗？ | 当前实现是词项命中加权、标题加权和余弦相似度融合，未采用 BM25 或 RRF。 |
| Reranker 用了什么？ | 当前使用规则和相似度融合排序，没有独立交叉编码器重排模型。 |
| 为什么这样切块？ | 配合短输入 Embedding 模型保留局部信息；重叠窗口缓解切分边界问题，当前参数尚需用检索评估验证。 |
| 和固定 RAG 流程的区别是什么？ | 模型可根据已获得的证据继续选择检索与读取工具；系统通过预算和证据校验约束过程。 |
| checkpoint、摘要和长期记忆有什么区别？ | checkpoint 保存运行状态；摘要压缩当前会话；长期记忆跨会话保存偏好与事实。 |
| 引用校验能证明答案正确吗？ | 能检查引用版本与已读范围；语义仍需要复核和实际业务验证。 |
| 使用 AI 编码后你负责什么？ | 结合一个具体案例解释需求、检索设计、框架选择、失败场景、修改依据和验收过程。 |

## 7. 最值得补充的成果证据

下一步优先建立一个小型问答评估集，例如先整理 30–50 个真实问题，覆盖故障改写、精确报警码、设备和版本不匹配、多步源码追踪、知识库无答案等场景。每题记录正确资料、必要证据和可接受答案。

建议对比词面检索、纯语义检索、混合检索，以及加入业务条件筛选后的结果，记录：

- **检索：** Recall@5 / Recall@10、MRR，以及不适用历史记录进入候选的比例。
- **回答：** 引用正确率、人工判定的答案正确率和无答案场景下的处理表现。
- **Agent：** 任务完成率、工具调用次数、token 用量和端到端延迟。

这些是后续评估建议，尚未执行，不能写成现有业绩。当前自动化测试验证了部分工具、状态与边界，不等同于完整 RAG 质量评估；完整后端测试仍有一个上下文压缩触发用例失败，准备演示时应继续跟进。

完成评估后，简历中“实现了混合检索”就能进一步补上有依据的效果、代价和取舍。
